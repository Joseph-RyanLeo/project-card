# D2-3 通用效果运行时

本阶段完成通用效果定义、战斗内运行实例、稳定事件队列、生命周期、叠加、来源修正与热诚。灰烬证册的38条活动效果可以通过严格类型校验，但尚未挂到真实卡牌；真实代表卡接入属于D2-4。

## 1. 功能整体如何运作

效果处理从一条触发事件开始：

1. `BattleEffectRuntime` 在固定逻辑时刻收到触发。
2. 它从已登记效果中找出 trigger 相同的候选，并按 AND 检查所有 conditions。
3. `BattleEffectTarget` 语义生成稳定排序的合法候选；需要随机时使用独立的效果随机流。
4. 目标选择和 operation 执行是两个事件。执行前会再次检查来源、条件和目标，失效时跳过，不自动改选或延迟重试。
5. 非瞬时效果生成 `BattleEffectInstance`，由 duration 和结束条件决定何时移除。
6. 数值修正通过目标的 `BattleModifierContainer` 按来源登记。实例结束时只撤销自己的贡献。
7. 每个步骤写入带父事件和根事件编号的结构化轨迹，可复现触发、条件、目标、叠加和结束原因。

同一份战前输入与种子，拆分帧推进、暂停后继续和1～3倍速度换算都应得到相同的效果轨迹与最终状态。

战斗实验室现提供八张固定效果测试卡，覆盖突击、持续、定时和其他友军行动后触发，以及刷新、同名接替、随机目标、行动后消费和封顶叠加。选择后会直接登记到本运行时，并在“分层轨迹”显示结构化效果过程；不另建第二套模拟规则。

强化和行动数值修正也会汇总到运行时卡面行动值。卡面用短促的减速跳数动画显示增加与消费后的回落；牌型倍率仍留在结算公式中，不混入卡面的基础行动值。

## 2. 关键数据与脚本职责

- `BattleEffectDefinition`：一条原子效果的严格定义，保存 trigger、conditions、target、operation、duration、stacking 和归属策略。
- `BattleEffectCatalog`：读取D2-1 JSON，拒绝未知枚举、缺失字段、重复ID和无效关联。
- `BattleRuntimeEvent`：一次待执行事件，保存整数逻辑时刻、稳定顺序、父事件、根事件和标签。
- `BattleEventQueue`：按“逻辑时刻→优先级→插入序号”排序。
- `BattleEffectInstance`：效果在本场战斗中的实际实例，保存来源、目标、开始/结束时刻、数值和结束原因。
- `BattleEffectRuntime`：协调触发、条件、选目标、执行、次数限制、递归保护、生命周期和日志。
- `BattleModifierContainer`：保存按来源拆分的加法、乘法和最低值修正。
- `BattleSquadState`：持有小队当前生命、护甲、规范化冷却进度和修正容器。

热诚是修正容器中的整数层数。实际速度为 `max(0.3, 1 + 热诚层数 × 0.05)`；普通行动间隔限制在0.5～99秒。小队保存0～1的冷却进度，因此速度变化不会重置已经完成的部分。

## 3. 初学者需要留意的 Godot / GDScript 写法

- `RefCounted` 用于纯规则对象。它不需要加入场景树，引用消失后由Godot自动回收，适合定义、事件和运行实例。
- `class_name` 让脚本类型可以在其他GDScript中直接用于变量和参数类型；拼错字段会比自由 `Dictionary` 更早暴露。
- 信号只负责把运行轨迹通知给外层；真正的规则顺序由事件队列决定，不能依赖信号连接顺序。
- 冷却进度是规范化数值，不直接把“剩余秒数”作为唯一真值。这样热诚变化时只需用新间隔重新换算剩余秒数。
- 效果目标与弹道使用不同的 `RandomNumberGenerator`。两者共享战斗种子，但不会互相消耗随机序列。

## 当前边界

- 已支持D2-3合成测试需要的数值、护甲、非行动伤害、热诚、强化与修改器操作。
- 38条活动效果的全部枚举都可严格解析；尚未实现的真实卡专用 operation 会写出 `unsupported_operation`，不会静默执行错误默认行为。
- 永久成长和战后写回留给D2-5；装备、法术、资源和商店仍按阶段计划后移。
