## 第一层：从输入到结果

准备阶段仍按原流程部署OwnedCard、装备和法术。Main在开战时交给BattleController阵容、战斗种子、备好法术、双方部署资源，以及玩家金币／双方整局开采累计的战前值。控制器先建立运行时状态，Main收到`battle_initialized`后映射原卡槽，再进入开场阶段，因此矿铃召唤能插在右侧，矿车立即行动也有正确的视觉来源。

突击、回响、遗愿由原效果执行器调度；矿脉规则响应实际事件。普通开采替换行动，金光妖在发射前锁定至多两张不同资源，击碎成功后每张资源各产生一次开采事件。条件法术先执行，继而唤醒守卫、召唤碎晶虫、应用采集者成长；资源收入进入实际赚取方的钱包，再触发贪魔和信徒。资源板与召唤物通过正式状态和信号同步到界面。

双方范围伤害先完成这一批的全部伤害，再统一处理死亡与遗愿。矿车、清障机等遗愿弹道完成前暂缓胜负；余烬明确保留已发出的主行动，即使它是己方最后一张牌也能先命中。普通无关在途弹道仍按原战斗结束规则清理。卡牌疲劳与30秒风暴独立结算，放逐暂停卡牌疲劳，风暴不伤害放逐单位。

本场数值、生命、光环、链接和钱包只在战斗内变化。永久成长、转火、纹章移除、偷款／返还、开采累计、哨兵销毁及装备耐久记入账本。正常战后先恢复快照，再由统一交易提交账本，移除耗尽或销毁实例；重复提交不重复奖励或消费。中断重开恢复战前状态，战中召唤物、动态资源与未提交变更一起撤销。

## 第三层：不直观的Godot / GDScript写法

- `.tres`是共享Resource。修改矿主的定义生命会影响所有矿主；某张卡永久转火必须改OwnedCard并走账本，不能改共享CardData。BattleSquadState则负责单场变化。
- `signal`让规则与界面分离：控制器发出召唤／资源／状态变化信号，Main据此创建或刷新实际卡槽，规则不依赖动画位置或视觉回调。
- `RefCounted`用于没有场景位置的数据和规则对象，适合钱包、链接、事件与账本。死亡公式会引用来源小队，清理时必须主动解除这些运行时引用，避免循环引用留下旧状态。
- `Array[OwnedCard]`、`Array[BattleEffectEvent]`等是强类型数组；JSON读出来的是普通Array／Dictionary，用`assign()`或逐项构造后再进入强类型接口，不能直接把普通空数组赋给某些条件表达式产生的强类型数组。
- `StringName`保存稳定ID；`match`按矿脉效果键响应。随机抽取使用控制器自己的RandomNumberGenerator，同一完整战前快照与种子可重现，界面刷新不重抽。
- `suppresses_echo`表示该动作明确不产生回响，避免幽魂矿镐附加开采递归；`waits_for_death_chain`表示遗愿或明确保留的弹道完成前不能判胜负。二者用途独立，不能用“来源已经死亡”粗略替代。
- 死亡快照在新增阵亡伤势前冻结行动公式和未用强化。遗愿重新选择合法目标，但不回读后来改变的牌型／数值；范围伤害则统一批次后再执行遗愿。

- `d2_6c_resource_battle_test.gd`：40项通过、3条失败。旧断言要求NPC收获不产生金币、卡牌、装备、纹章、成长或伤势变化；本轮确认已取代此规则。无OwnedCard的NPC现在会建立独立战斗实例，从而正确获得资源成长，奖励仍不转给玩家。
