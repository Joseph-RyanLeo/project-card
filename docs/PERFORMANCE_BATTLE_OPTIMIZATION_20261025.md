# 战斗与结算性能优化第二轮（2026-10-25）

## 范围

只减少重复查询、重复快照恢复及重复界面刷新。没有更改目标优先级、随机抽取顺序、行动和命中时序、成长及奖励规则，也没有减少弹道、换位、阵亡、数字补间或卡牌动画。正常游戏内部仍不增加黑场。

## 第一层：输入到结果的流程

### 高压战斗

一次目标查询先按原规则过滤、分层，再计算候选权重并抽签。以前求权重总和与寻找抽签边界会重复计算同一候选的符文、状态和前排遮挡；现在本次查询保存权重数组，找边界时直接读取。攻击者是否带有效弯刀、场上是否有存活太阳，也改为每次查询读取一次，而不是逐候选重新扫描。

数据只在这次函数调用内复用，不跨行动或帧缓存。下一位行动者仍会重新查询，因为上一位可能解除影蔽、消耗增援或改变阵容。零权重层仍跳过、不抽随机数；合法层只抽一次，候选顺序不变。

### 战斗结算

原流程先完整恢复准备快照并重建四排，再由结算服务再次恢复收藏，随后刷新收藏；迷宫还会额外刷新一次收藏和奖励面板。

现在保持原阵亡演出结束后才进入结果页，在同一个同步调用中：

1. 结算服务按原事务提交：校验账本、恢复战前收藏、应用成长与消耗、发奖、登记已提交。
2. 成功时只恢复四排的战前排列，不再把已提交收藏或已消耗资源回滚。失败仍走完整准备快照恢复。
3. 映射原成员统计、处理贴纸奖励，统一刷新一次收藏及资源显示，更新结果和迷宫界面，最后照常保存。

永久销毁的成员仍在原位显示本场统计，但不回到权威收藏；消耗的装备不再出现在结算卡面。重复打开结果不复活已销毁成员，也不回滚成长、重复发奖或再次消耗法术。

## 第二层：脚本、数据与职责

- `scripts/battle/battle_controller.gd`：`choose_weighted_target()` 和资源混合目标查询保存局部 `weights`；`choose_base_target()` 去掉多余预求和。太阳查询在单次目标选择内共享，公开耀眼查询仍实时读取。
- `scripts/main.gd`：`_show_battle_result()` 统一管理结果页刷新；`settle_current_battle(false)` 只提交数据、不在中途重建收藏，默认参数仍保留直接结算调用的刷新行为。
- `_restore_battle_rows()` 复用原四排恢复代码；`_restore_battle_result_layout(false)` 使用已提交状态恢复结果布局。独立调用的默认完整恢复行为没有取消。
- `_restore_row_from_snapshot()` 的 `retain_removed_members` 只用于结果统计归档，其他恢复入口仍过滤已不属于收藏的成员；已消耗装备始终过滤。
- `scripts/flow/short_maze_controller.gd`：仍计算奖励、经验和迷宫状态，不再和Main重复重建收藏。其唯一生产调用方Main负责刷新；直接结算默认刷新，结果入口在最终阶段刷新。
- `OwnedCard`、战前快照、三个账本和结算日志仍分别负责实例状态、回滚源、战中变化与防重复提交；结算服务本身未改动。

## 第三层：容易陌生的写法

`Array[int]` 是只存整数的有类型数组。`weights[index]` 和同位置候选一一对应，不会产生第二套玩法权重，也不是全局缓存。

`refresh_collection: bool = true` 是默认参数：旧调用不用补参数。只有结果入口明确传 `false`，因为它会在全部奖励提交后统一刷新；不是使用 `await` 延后规则，也不会让玩家在未提交时操作。

Godot的Resource按引用共享。快照阵容仍引用原OwnedCard，所以结算成长写入同一实例后，重建卡面能读取最终值；不能用恢复战前收藏的方式再次构建已提交结果，否则会撤销奖励。销毁成员的对象可供统计展示，但是否拥有该卡仍只看收藏容器。

## 原生窗口对照

Apple M4、Godot 4.7.2、1280×720真实窗口、关闭垂直同步。探针保留正式Main、正式控制器、特效、日志和保存；计时子类只调用 `super` 包裹原实现，不替代业务。以下是本机样本，不是所有设备的帧率保证。

### 结算

固定72张底仓卡、固定实例随机种子与资源板；6对6和14对14各3次，结算前实际跨排换位。这里直接调用正式结果入口以隔离测量提交与显示恢复，不把阵亡演出时长当成CPU开销。自然战斗至结果的链路另由现有晶体化专项覆盖。

| 指标 | 优化前 → 优化后 |
| --- | --- |
| 6对6同步CPU中位数 | 48.68 → 36.58毫秒，下降约25% |
| 14对14同步CPU中位数 | 73.79 → 59.70毫秒，下降约19% |
| 6对6结果帧中位数 | 59.08 → 47.27毫秒 |
| 14对14结果帧中位数 | 90.20 → 75.21毫秒 |
| 成功结果完整准备恢复次数 | 1 → 0，服务内部权威恢复仍保留 |
| 普通结果资源显示刷新次数 | 2 → 1 |

首个冷结果帧优化后仍出现97.69毫秒，不能宣称最坏整帧卡顿已解决。四排节点重建和存档仍为主要剩余开销；未通过隐藏保存、减少卡面或延迟结算来获得数字。

六组完整保存状态逐字段对照一致，仅排除未参与本探针奖励抽取、由启动时随机初始化的商店 `rng_seed` / `rng_state`。资源板、收藏、阵容、成长、提交身份及其他持久字段均一致。

### 高压战斗

28张真实随从、0.5秒冷却、三暗符文，预热10帧后每场240帧、固定逻辑步长1/60秒。第二场每6帧额外做4次真实跨排交换，共160次，保留正常自动换位；弹道分别507和570次。

| 指标 | 优化前 → 优化后 |
| --- | --- |
| 密集场基础行动选择总CPU | 136.92 → 107.10毫秒，下降约22% |
| 换位场基础行动选择总CPU | 152.22 → 121.06毫秒，下降约20% |
| 密集场单次基础行动选择峰值 | 22.76 → 17.76毫秒 |
| 换位场单次基础行动选择峰值 | 29.14 → 22.82毫秒 |
| 密集场整帧P95 | 27.27 → 26.04毫秒，小幅改善 |
| 换位场整帧P95 | 36.42 → 36.25毫秒，基本不变 |
| 换位场整帧最大值 | 66.93 → 58.84毫秒，仍有尖峰 |

两场原生对照的起始规则、457/500条完整效果时间轴、最终随机状态均完全相同，不只比较最终胜负。局部查询的计算收益明确，但渲染、卡面同步与其他规则批处理仍占帧预算，不能把查询耗时下降说成整场帧率提升20%。

曾采集的无窗口不同进程换位场时间轴出现差异，未用它证明规则等价。补充同一真实状态、同一随机起点下旧算法和新实现逐次对照，避免把不一致的样本当作性能收益；旧算法只充当测试对照，实际返回值来自正式新实现。
