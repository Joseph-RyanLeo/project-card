# 疲劳阶段性能优化（2026-10-08）

## 现象与依据

伙伴重启后的两份 JSON 记录同一场第7天战斗：种子463294128，疲劳后仍能结束并取得胜利。战斗文件约44.78 MiB，本局诊断约52.31 MiB。战斗时间轴44326条中，43756条为效果追踪；30～32秒的追踪频率约为20～29秒的5.47倍。文件没有逐帧FPS，不能据此证明最初卡死的唯一原因。

## 第一层：运行流程

每次伤害仍即时检查持续效果，但先比较其依赖事实。生命是否归零、护甲是否清空、站位、来源、装备、伤势、符文或相关取值改变时才重新排入效果队列；仅生命减少且条件仍成立时，不重复安装已有持续效果。破甲、死亡、召唤与复活仍按原来的即时顺序处理。

战斗状态多次变化时，卡面和战斗日志合并为一次延后刷新。资源板保留即时同步，以满足召唤资源的动画锚点；内容未改变时不销毁和重建节点。

诊断默认保留行动、公式、整数结算、实际执行变化和失败原因，省去成功条件检查、已安装效果和重复持续选目标的追踪；导出 JSON 使用紧凑格式。完整追踪可用用户启动参数 `--trace-battle-effects`，或开战前设置 `effect_runtime.full_trace_enabled = true`，它仍只记录实际执行的检查，不恢复无用的重复调度。

疲劳伤害按计划触发时间计算，避免29.999999…秒被误算为0点。30秒起每秒结算，序列保持设计规定的1、1、2、2、3、3……。回放还发现NPC纹章安装调用不存在接口，已改用小队现有的可见纹章槽索引接口。

## 第二层：脚本与数据职责

- `battle_effect_runtime.gd`：保存条件输入快照，跳过不变的复检；`filtered_trace_counts`记录省去的追踪数量。
- `main.gd`：合并卡面与日志刷新；同步资源板。
- `resource_preparation_tray.gd`：保存资源板显示快照，只在布局、实例或显示生命改变时重建。
- `card_view.gd`：相同显示值不重新刷新；清除未启用的覆盖状态直接返回。
- `battle_controller.gd`：按计划时刻计算疲劳数值，安装NPC纹章。
- 两个诊断序列化脚本：写紧凑JSON；战斗采集器标注 `trace_detail` 与过滤计数。文件结构版本仍为1。

## 第三层：GDScript写法

`call_deferred()`在当前调用链完成后执行刷新。布尔排队标记阻止同一轮状态信号重复预约；它只合并显示更新，不推迟规则结算。

`duplicate(true)`复制嵌套数组和字典，避免资源板原地修改时连旧快照一起变化；Godot对象仍保留同一个引用。阵容参数使用 `Array[Dictionary]`，普通嵌套空数组无法传给严格类型参数。

## 验证与边界

使用正式Godot 4.7.2、真实Main场景、正式控制器与伙伴战前存档，测试存档均位于 `/private/tmp`。所有进程串行并显式指定日志文件，没有运行全量套件。

- 新疲劳专项含真实伙伴回放：136项、0失败；补查计数依赖后单位部分125项、0失败。
- 30/60/144帧步进得到相同疲劳伤害序列；护甲条件恢复、失效与来源死亡均即时生效。
- 精简与完整追踪的行动时间、目标、伤害顺序及控制器随机终态一致，均35秒胜利并正常显示结算。
- 现有持续效果执行器、矿脉运行时256项、矿脉Main18项、单场诊断导出通过。
- 真实本局诊断导出、JSON读回、完整战斗时间轴和导出不改写存档通过。
- 旧本局诊断套件所用33卡样本未通过Main加载，后续访问缺失阵容并超时；没有修改该套件断言。当前伙伴存档的正式导出已单独验证。
- 用户实际存档SHA256保持不变；`git diff --check`通过。

本机无窗口回放默认单场JSON为2090300字节（约1.99 MiB），本局诊断约2.38 MiB；默认疲劳帧样本95分位约18.8毫秒，最大约56.6毫秒，包含战斗结束处理。完整追踪为约10.24 MiB，最大帧约198.5毫秒。环境与伙伴Windows游戏不同，以上不是Windows实测FPS；仍需伙伴用重新导出的版本复测。

已经导出的旧大文件不会自动缩小，新采集的战斗使用新模式。旧文件可留在本机目录供读取，或打ZIP后转交。
