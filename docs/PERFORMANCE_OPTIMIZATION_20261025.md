# 性能优化第一轮（2026-10-25）

## 本轮范围与结果

保留两项小改动：装备绑定后复用未变化的收藏卡面；开战时让奖励目录与资源板定义查询共用一次卡牌目录结果。没有修改规则推进、伤害／奖励时序、符文揭晓、动画、吸附精度、存档格式或黑场范围。

装备松手得到明确改善；开战仅有小幅波动，不能宣称稳定提速。结算与密集换位的慢帧尚未解决，本轮没有改写快照恢复或战斗规则循环。

## 第一层：输入到结果

装备松手仍先完成合法性检查与精确吸附，再更新原物品实例的小队归属、刷新目标指示物、选择卡牌并更新准备预览。区别是收藏更新改用已有的局部复用路径：未变化的收藏槽和CardView继续存在；装备从未部署变为已部署时，对应收藏槽仍重建为不可拖动虚影。跨小队移动时装备仍已部署，因此其收藏虚影也能直接复用。

开战仍正常建立快照、保存战前状态并初始化控制器。原先 `_build_reward_card_catalog()` 内部已经完整构建过卡牌定义表，随后构造资源板上下文时又重做一次。现在把同一批CardData分别组织成排序的奖励数组和按ID查询的字典，避免在同一个开战调用内重复扫描。它不是跨帧缓存，下次开战仍读取当前目录、持有实例与战场覆盖。

## 第二层：脚本、数据与职责

- `scripts/main.gd` 的 `_equip_item_on_squad()` 改为 `_build_collection_cards(null, null, true)`；沿用原有 `reuse_unchanged` 参数，不增加新刷新队列或额外状态变量。
- `_build_collection_cards()` 原有逻辑按OwnedCard引用寻找可复用槽，并比较 `is_deployed_ghost`。状态改变的目标槽仍正常重建，不是跳过整个收藏更新。
- `start_battle()` 的局部 `reward_catalog` 保存原排序目录，`card_registry` 用同一批资源建立ID查询；资源板只按ID查找，不依赖字典插入顺序，奖励数组顺序保持不变。
- `OwnedCard` 仍保存实例身份、符文揭晓与永久状态；本轮只减少显示节点重建与重复查询，不复制或替换这些实例。
- `tests/equipment_collection_reuse_test.gd` 用真实2K窗口及鼠标检查节点、符文覆盖层身份、部署虚影、信号连接和跨小队装备归属，不替换业务函数。

## 第三层：容易陌生的写法

`_build_collection_cards(null, null, true)` 的前两个参数表示本次没有特别指定一张入场动画卡，第三个参数才表示复用未变化节点。采用已有接口而不是另写一套局部刷新逻辑。

GDScript中的Resource和Node都是引用对象。卡牌内容看起来相同，不表示它们是同一张OwnedCard或同一个CardView；专项检查直接比较对象引用，并确认未知符文仍使用原来的遮罩节点。

局部 `Dictionary` 只是为同一批CardData增加按ID查询的索引，不产生第二份卡牌定义，也不在下一次开战继续使用旧目录。这里刻意没有加入永久缓存、定时过期或文件监控系统。

## 装备前后对照

Apple M4、Godot 4.7.2、真实2560×1440窗口、内部1280×720，使用上一轮相同的临时成功松手探针，每轮3次实际绑定；资源入板、法术入队及板内重排也实际完成。下表比较两轮最大值，非普遍设备帧率保证。

| 指标 | 优化前 → 优化后 |
| --- | --- |
| 装备松手整帧最大值 | 37.64 → 27.59毫秒，约下降27% |
| 松手输入分发同步CPU最大值 | 21.82 → 13.44毫秒 |
| 收藏刷新分段最大值 | 10.63 → 1.89毫秒 |
| 提交信号到第一帧绘制最大值 | 32.88 → 22.93毫秒 |

优化后三次装备松手帧约26.18、27.08、27.59毫秒，未再超过33.33毫秒，但仍高于16.67毫秒的60FPS预算，不能说已彻底消除短顿。准备预览刷新仍约4.3～4.6毫秒，未通过延迟数据更新或省略光环计算绕开。

## 开战与结算的边界

同一全模块临时探针、六对六、战斗种子20261024，增加子类计时包裹正式实现，未替换规则函数。不同进程的初始自动资源与环境时序未保证逐事件完全相同，因此小幅变化不视为稳定收益。

| 指标 | 本轮修改前 → 最终版本 |
| --- | --- |
| 开战同步CPU | 30.73 → 29.59毫秒，变化较小，不作稳定收益结论 |
| 开战所在帧 | 38.89 → 37.64毫秒 |
| 持续战斗帧P95 | 10.89 → 11.19毫秒，基本同一水平 |
| 结算同步处理 | 46.48 → 55.68毫秒，未改善 |
| 结算帧 | 61.78 → 72.29毫秒，仍有明显尖峰 |

结算函数、快照恢复函数和规则循环本轮未修改。分段测量中，最终版本快照恢复约33.84毫秒、结算事务约12.97毫秒、保存约5.13毫秒；后续应继续拆分阵容恢复与显示重建，而不是宣称结算已经优化。

曾试验复用已加载的资源引用，同时逐次比较目录路径。单独探针表明目录枚举本身仍约3.2～3.5毫秒，这个方案没有稳定收益，已经连同专用试验测试撤回；没有留下额外缓存字段或兼容分支。
