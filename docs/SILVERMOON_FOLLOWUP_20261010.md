# 2026-10-10 银月后续修复

## 结果与证据

- 随机收藏奖励：未指定主题时原来遍历全部注册定义，包括扭曲矿脉。现复用普通商店的本局开放候选池；明确主题的特殊奖励仍保留自己的规则。附件中未发现晶皮哨兵、矿灯鬼火的实际拥有实例，故不能据附件断言两张卡的具体获得时间；修复的是确定存在的卡池泄漏。
- 晨昏守卫：光环使用保留的负数来源ID，通用关键词登记却拒绝全部非正数，导致耀眼登记失败。登记现接受非零来源，正数给通用效果实例、负数给内容光环；换排时沿用同一来源撤销，不影响其他耀眼来源。
- 结算统计与重复舞者：战斗换排改变了`row_key`，结算却用当前排和战前索引找槽。延迟刷新随后因装备不同将运行时小队重新写进错误槽，覆盖守卫或其他卡，产生同一舞者实例的第二份部署。现保存`initial_row_key`、按战前排与索引显示统计，并让结算阶段拒绝战斗状态刷新。永久生命成长也加入文字结算摘要。
- 敌方纹章：第1–2天0枚、第3–4天1枚、第5–6天2枚、第7–8天3枚，逐张随从计算，随机I级、受槽位限制。首次生成遭遇时入快照，读档不重抽，已有遭遇保持原快照。
- 伊尔：双方小队分别比较有效光暗净差，净光每枚永久生命+2、净暗每枚永久数值+1，相等无变化。有效符文包括已揭晓、显现且未遮蔽的底层符文或覆盖贴纸。生命归生命来源卡，数值归行动来源卡；本场立即生效，正常结算才提交。
- 祭祀：启咒链接两个敌军，仅下一次近战／远程／法术攻击行动消费链接并攻击另一目标；治疗、防御及独立效果伤害不消费。同来源再次启咒覆盖旧链接。
- 编者：突击获得1张月露，按阵营登记奖励，玩家正常战后入收藏。
- 均衡文案本轮只列清单，等待用户提供三套文本：伊尔、晨昏骑士、晨昏守卫、晨昏元素、星月豹；日月护符是按排变化的装备。

## 给开发者的三层说明

### 一、输入到结果

开战先记录收藏和战前阵容，再为每个小队建立战斗状态。换排只改变战斗状态和卡面位置；战后恢复原阵容，以战前排和索引定位每张统计。永久成长及获得的月露先进入账本，正常结算才写入`OwnedCard`，中断战斗则回滚。敌方纹章在遭遇生成时就确定，后续直接恢复同一份快照。

### 二、关键文件与数据

- `scripts/main.gd`：随机奖励候选筛选、快照恢复、结算统计与卡面刷新。
- `scripts/battle/battle_squad_state.gd`：`row_key`与`formation_index`是战中位置；`initial_row_key`与`initial_formation_index`是战前位置。`runtime_permanent_action_growth`保存本场已生效、战后才提交的永久数值。
- `scripts/battle/silvermoon_runtime.gd`：`balance_growth()`按小队光暗净差登记伊尔成长；`links`保存祭祀的两个链接目标；`on_action_launched()`只让真实攻击行动消费链接。
- `scripts/flow/enemy_encounter_builder.gd`：为每张敌方随从确定纹章种类与槽位。
- `data/demo2/short_maze_content.json`：`enemy_emblems_by_day`保存第1至第8天的纹章数量。
- `OwnedCard.instance_id`是单卡唯一身份；卡面节点是显示载体。同一ID被显示两次并不代表新增了第二张拥有卡，因此两份显示会读取同一套成长和贴纸。
- `scripts/battle/battle_diagnostic_recorder.gd`：额外记录有效耀眼、影蔽和运行时关键词，便于后续查证。

### 三、较难的写法

- `call_deferred()`会把调用排到稍后执行：发起时仍在战斗，执行时可能已经结算。因此刷新函数必须读取执行当时的阶段，不能把旧状态写回已恢复的阵容。
- `StringName`适合反复比较的ID、关键词和排名称；它表示稳定名称，不能替代`OwnedCard`的实例归属。
- 来源ID允许正负数，只有0表示无来源。负数是现有内容光环的保留命名空间；获得、撤销必须使用同一ID，避免移除其他来源。
- 账本保存明确的永久变化；不通过战前战后面板数值差额反推成长，因为装备、符文和光环也会改变面板。

## 旧存档恢复

`repaired-saves-20261010`目录的两份文件从附件的`saved_checkpoint`提取，只移除同一舞者实例的第二份部署，保留其成长、贴纸和装备，不改写原诊断附件。两份修复文件通过正式存档解码验证；它们是存档文件，不是完整诊断包。
