# D2-5 唯一实例与战后结算计划

D2-5 负责把 D2-4 的战斗侧待结算记录安全写回本局状态。权威规则仍以 `GAMEPLAY_DESIGN.md` 为准；本文记录实现顺序和当前边界。

## 小步顺序

1. **唯一实例与战前快照**：建立 `OwnedCard`、本局收藏容器、实例与 `SquadData` 的绑定，以及能够回滚实例状态和四排阵容的战前快照。
2. **统一战后事务（已完成）**：正常战斗结束时先恢复战前状态，再按战斗实例 ID 消费永久成长和本局奖励；整批成功后登记一次性提交凭证。
3. **纹章、伤势、耐久与进度（已完成结算协议）**：接入永久纹章、伤势、法术耐久、种子进度和进化的实例级战后协议；具体内容生成与目标选择留给各玩法系统。
4. **主流程与存档回归（已完成）**：接通中途退出、重试、正常继续和存档恢复，验证连续重试、重复结算、同名实例与临时来源边界。

## 第一小步已完成的数据基础

- `CardData` 继续只表示共享卡牌定义；不会承载某一张收藏卡的永久成长、伤势或纹章。
- `OwnedCard` 用本局唯一 `instance_id` 表示玩家实际拥有的一张卡，并独立保存永久成长、伤势槽、纹章槽、符文揭晓、耐久和来源进度。
- `OwnedCardCollection` 负责生成不重复的实例 ID，并能按实例 ID 精确恢复战前收藏；同一 `CardData` 可以生成多张互不污染的实例。
- `SquadData` 保留现有 `CardData` 显示接口，同时绑定对应 `OwnedCard`。小队复制、拆队和双卡整队合并会保留或清理正确的实例绑定。
- `BattleEffectOwnerRef` 同时保存本场 `runtime_id` 和跨战斗 `owned_card_instance_id`。前者只定位本场状态，后者才是永久写回目标。
- 永久成长与本局奖励账本的每条记录都带 `battle_instance_id` 和稳定 `entry_id`；永久成长还带实际受益的卡牌实例 ID。
- `BattlePreparationSnapshot` 在正式开战前保存收藏实例状态、固定种子和四排阵容。中途重试先回滚实例状态，再重建阵容。
- `RunSettlementJournal` 提供正常战后一次性提交凭证；第一小步先建立防重复基础，第二小步已接入正式消费事务。

## 第二小步已完成的统一结算

- `BattleSettlementService` 是正常战后唯一写回入口。它先校验战斗 ID、条目 ID、成长属性、奖励种类和收藏实例，再恢复战前收藏并整批写入。
- 永久行动值和基础护甲成长按 `owned_card_instance_id` 写入实际受益卡牌，不修改共享 `CardData`。下一场战斗会从 `OwnedCard` 读取成长后的基础行动值、最大生命和基础护甲。
- 金币写入 `RunRewardState.gold`。征召官的随机随从请求完整保留筛选参数并进入待解析队列，等待 D2-7 正式卡池和唯一性规则，不临时伪造随机卡。
- 所有写入成功后才由 `RunSettlementJournal` 标记整场已提交；同一战斗再次结算只返回 `already_committed`，不会重复成长、发金币或追加请求。
- 若任一条记录不合法或写入失败，收藏与本局奖励状态一起回滚，不留下半份结算。
- 中途重试仍恢复战前实例状态；已经正常提交的战斗返回当前开发版准备界面时，不再用旧快照抹掉已提交成长和奖励。

## 第三小步已完成的实例变化协议

- `BattleOwnedCardChangeLedger` 只记录已经由未来玩法系统确认的槽位结果与种子进度，不在结算层猜伤势类型、纹章掉落、升级路线或随机目标。
- 伤势与纹章通过 `owned_card_instance_id + slot_index` 精确写入；槽位越界、状态字段不完整或同槽重复写入会使整场结算失败并回滚。
- 每枚纹章使用独立 `instance_id`。种子进度按该 ID 保存；同一实例在原槽进化时保留进度，替换成另一枚纹章时清除旧来源进度，临时纹章的进度明确跳过。
- 法术实例在获得时按 I～V 品级初始化为 1～5 耐久。战前快照记录本场实际准备的法术实例；正常战后各扣 1，归零后移出收藏，中途重试与重复提交都不会重复扣除。
- 上述变化与永久成长、金币、随机卡请求共享同一个原子事务：全部成功才登记该战斗已提交，任一步失败都会恢复收藏和奖励状态。

## 第四小步已完成的主流程存档恢复

- `RunSaveService` 将内存中的 Resource 引用转换为可写入 JSON 的稳定 `card_id + resource_path`，并使用版本号拒绝误读不兼容结构。
- 存档包含唯一收藏实例、永久成长、伤势、纹章、种子进度、法术耐久、四排阵容、固定战斗种子、本局奖励、实例序列与已提交战斗 ID。
- 战斗中保存时写入战前安全快照，而不是正在变化的战斗状态；读档统一回到准备阶段，并让下一次开战复用原战斗实例 ID 与固定种子。
- 正常结算后保存的是已提交状态。读档恢复 `RunSettlementJournal`，因此同一战斗即使被旧界面信号或重复调用再次送入结算，也只返回 `already_committed`。
- 同名卡通过各自 `OwnedCard.instance_id` 重新绑定阵容；磁盘往返后伤势、纹章和成长不会串到另一张同定义卡上，后续新增卡也继续使用不重复的实例序列。
- `Main` 提供 `save_run_to_path()` 与 `load_run_from_path()` 作为正式流程入口。具体自动保存时点、继续游戏按钮和玩家存档槽 UI 仍跟随 D2-7 的商店/事件流程统一接入，避免当前测试主场景擅自覆盖未来正式存档。

## 当前刻意保留的边界

- 主收藏 UI 暂时仍以 `CardData` 绘制和筛选，由 `OwnedCardCollection` 派生兼容数组；D2-7 获得同名重复卡前需要把拖拽选择也迁移为实例 ID。
- 伤势类型与升级表、纹章效果与随机合法槽选择、法术准备栏 UI、种子参战/存活判定仍未上线；当前完成的是这些系统以后可直接调用的一次性结算协议与自动测试。
- 随机随从请求只完成一次性转存，真正抽取仍等待 D2-7 的本局开放卡池、IV级持有去重和替代奖励规则。
- 主界面尚无正式金币栏与随机奖励揭晓流程；当前可通过结算状态和自动测试验证写入结果。
- 当前已有本局 JSON 存取入口，但还没有正式存档槽、继续游戏按钮及事件/商店自动保存触发；这些属于 D2-7 的完整单局流程，不影响 D2-5 数据往返正确性。
