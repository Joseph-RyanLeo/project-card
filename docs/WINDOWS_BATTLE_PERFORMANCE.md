# Windows 战斗性能日志采集

此采样器默认关闭。开启后会在内存中汇总数据，不逐帧写日志；按 **F10** 时一次性写出 JSON。

## 开启与采集

1. 在 Windows 上打开 PowerShell，切到导出游戏所在文件夹。
2. 在当前 PowerShell 窗口设置开关并启动游戏：

   ```powershell
   $env:PROJECT_CARD_TRACE_BATTLE_PERFORMANCE = "1"
   .\ProjectCard.exe
   ```

   每次新开的 PowerShell 窗口都要重新设置环境变量。也可以在 Windows 用户环境变量中长期添加同名变量，值设为 `1`。
3. 进入准备阶段，用同一件装备分别拖过随从卡边缘几次，再松手完成放置；这会记录拖动候选和松手精确吸附的耗时。
4. 开始一场战斗，等战斗中至少出现几次攻击弹道和元素特效。
5. 在游戏窗口按 **F10**。游戏状态栏会显示写入成功，提示的完整路径可悬停查看；如果从终端启动，终端也会显示路径。
6. 把生成的 `battle-performance-*.json` 发回即可。若是 PowerShell 窗口启动，日志在 `%APPDATA%\Godot\app_userdata\Project Card\logs`；Godot 的 `user://` 默认目录会随项目配置变化，可用 F10 输出的完整路径定位。

## 日志字段

- `frame_ms`：Godot 传给主界面每帧的时间间隔；汇总包含 p50、p95、最大值，以及超过 33ms 的帧数。
- `wall_frame_ms`：相邻主循环采样点之间的独立真实时间，首样本为0，避免引擎delta限制掩盖长阻塞；包括暂停、后台等待和F10写日志，不能全部归因为游戏计算。
- `phase`：0准备、1战斗、2结果；`shop_open`、`collection_page`、`native_drag_active`、`click_carry_active` 用来核对尖峰所在界面和输入路径。
- `collection_page_turn_ms`：本帧成功翻页入口的同步构建耗时；不包含整段 Tween 等待或 GPU 绘制。
- `battle_start_ms`：本帧成功开战时的清理、快照、阵容和初始卡面构建耗时。
- `battle_result_ms`：本帧进入结果页、恢复阵容、结算奖励与保存存档的同步耗时。以上字段与其他脚本耗时可能包含同一工作，不能相加；旧采样缺字段表示未测量。
- `drag_preview_ms`：修复版同时覆盖点击携带与原生长按拖放的候选更新；原生拖动只计目标更新，不与点击外层重复相加。旧V0.2.70仅统计点击携带，因此旧日志的0值不能证明没有长按拖动负担。
- `release_exact_snap_ms`：松手时的装备贴图遮罩精确搜索。
- `battle_advance_ms`：`BattleController.advance_time` 的累计脚本耗时。
- `state_sync_ms`：战斗状态刷新到卡面节点的脚本耗时。
- `effect_dispatch_ms`：弹道发射与效果结算回调中，创建表现和日志的脚本耗时。
- `battle_effect_children`、`draw_calls`：当帧特效层子节点数和渲染器报告的绘制调用数，用来对照特效数量与帧时间。

`effect_dispatch_ms` 测量特效事件的脚本分发和创建开销；Tween 后续更新与 GPU 绘制包含在总帧时间里，Godot 不会把它们单独拆成该特效层的 GPU 耗时。
`battle_advance_ms` 包含同步发出的状态和效果回调，因此它与 `state_sync_ms`、`effect_dispatch_ms` 是包含关系，不能相加当作总耗时。

## 对比条件

测试前先关掉其他高负载程序；固定窗口大小、显示器刷新率、渲染器、游戏速度、阵容与种子。至少采集一份空闲准备阶段和一份战斗阶段日志；如果要比较版本，每个版本重复相同操作数与战斗时长。不要把窗口切到后台，因为系统会降低后台窗口的帧率。

本功能没有改变战斗规则。先用这份数据区分拖动预览、战斗时间推进、状态同步、特效事件创建与整体帧时间，再判断是否需要针对 Windows 做进一步优化。

## 2026-09-26 更新前基线

已有 Windows 采样文件 `battle-performance-2026-09-26_21-47-13.json` 含 7,330 个整帧样本，其中 1,135 帧记录到战斗推进，战斗推进累计 16,047.202ms、中位数 12.606ms、最大值 111.722ms；状态同步在这些推进调用内部，不能与推进耗时相加。原日志还记录 16 帧超过 33ms。拖动精确吸附最大值为 2.395ms，拖动预览最大值为 24.327ms。该文件没有提供槽位枚举、贴纸节点创建或符文重建计数，因而只能作为改动前的整体脚本耗时基线，不能用来声称某个子路径贡献了多少耗时。

旧版无条件刷新本来就存在；这次诊断另外找到几处重复工作：读取实例槽位前先枚举所有备用排列、随后丢弃；伤势更新会重复重建状态；空槽绘制会重复计算槽位；同值符文覆盖也会重建符文节点。已改为优先读实例已保存布局、备用排列惰性缓存、合并状态提交、同值早退并复用节点。默认布局缓存按伤势／纹章槽数索引并返回独立数组；实例布局读取不填充默认缓存，随机候选与随机数调用保持原样。

旧记录曾写“本轮环境未发现 Godot”，该判断不再适用于本次收尾：当前机器已确认存在 Godot 4.7.2。以下新旧版数据来自伙伴在 Windows 上提供的两份 JSON；原始文件 `/Users/Zhuanz/Downloads/更新前.json` 与 `/Users/Zhuanz/Downloads/更新后.json` 只用于读取和统计，没有复制进仓库。

## 2026-09-27 更新后对比

两份日志均为 Windows、1280×720。筛选 `battle_advance_ms > 0` 的活跃战斗帧后，更新前有 2,220 帧、更新后有 4,871 帧；两份日志的 Godot `delta` 累计都约 31 秒。每帧推进均值由 11.736ms 降至 4.229ms，推进内部的状态同步均值由 8.317ms 降至 2.793ms。`state_sync_ms` 包含在 `battle_advance_ms` 中，不能相加。引擎 `frame_ms` 均值由 13.949ms 降至 6.363ms，P95 由 18.519ms 降至 6.944ms；战斗样本中超过 33ms 的帧由 8 次降至 0 次，最大值由 68.849ms 降至 27.260ms。

数据限制：两份文件没有阵容、种子、倍速或硬件信息，所以不是严格受控实验；`frame_ms` 是 Godot 提供的引擎帧间隔，不是独立测出的呈现耗时。用户反馈更新后“基本没问题”，表示体感改善但不代表所有问题消失。后段疑似重开时出现连续尖峰（更新前 76.466／67.089ms，更新后 73.010／42.420ms），日志没有事件标记，无法确认尖峰归属。拖动预览 P95 为 0.329→0.276ms，但最大值 13.582→16.475ms；精确吸附每版仅2个样本，最大值 1.989→7.478ms，样本不足以判断退化或改善。

后续只保留观察项，不新增大型采样系统：若 Windows 上仍能稳定复现卡顿，再同设备、同阵容／种子与倍速测量战斗、拖动和重开。工程上优先删重复工作；显示查询不生成业务状态、不消耗随机数；没有状态变化就不重建节点；按阶段测量。Mac 或 headless 结果不能替代 Windows 体感验证。
