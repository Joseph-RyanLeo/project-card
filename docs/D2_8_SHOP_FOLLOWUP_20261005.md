# 商店截图反馈修正与学习说明（2026-10-05）

在主项目目录、main分支顺序修改。此文取代前轮实施说明中“槽内仅显示目标副本／不搬离来源”和“新卡点可在所有卡面出现”的描述。当前规则以GAMEPLAY_DESIGN、GAMEPLAY_RULE_DETAILS、CARD_CHARACTER_DESIGN为入口。

## 1. 整体功能与输入到结果

| 反馈 | 完成后的行为 |
| --- | --- |
| 商店层级 | 商店面板盖住战场的牌型提示和装备指示物；商店自身卡面提示及检视仍可打开。 |
| 新卡绿点 | 只有新加入收藏的卡牌在收藏卡面显示。资源板详情、战场、商品预览和检视不显示，也不因此清除收藏标记。 |
| 哨位库存 | 共用指示物板固定在设计画布右下角；商店／收藏／战場切换不会把它滚出屏幕。库存只显示已有哨位图标，移除数量标签。 |
| 随机卡领取 | 征兵册等奖励在战斗结算直接入收藏，并显示实际卡名；商店删除手动领取按钮。一本征兵册获胜给两张，两本给四张。 |
| 目标卡槽 | 拖入后临时移动原卡面，来源为空，不创建快照卡面。槽内支持点击抓取、长按拖动和取消；放回收藏时恢复原来源，退出事件／服务自动归还。 |
| Esc还原 | 先归还目标卡、终止商店动画并关闭旧商店，再恢复初始运行及流程界面，不留下空商品商店。 |

目标卡槽只临时保管显示节点。OwnedCard仍是唯一拥有实例，原部署绑定保留，以便退出时恢复原状。强化确认写入永久成长；出售和撕卡确认时先归还节点，再执行原事务。保存失败回退卡牌、部署、装备、贴纸、金币和目标选择。新局、读档、还原和收藏重建也先归还，避免来源节点被清理时丢失卡面。

战斗随机卡奖励流程为：检查重复结算 → 恢复战前收藏 → 写成长及奖励 → 消耗征兵册等明确消耗 → 按请求筛选与抽卡 → 创建OwnedCard → 标记战斗已提交。候选无效时回退整份事务，随机源不前进；重复结算和读档不重复发奖。旧存档遗留的待解析请求在加载后自动解析并保存。

五张卡牌的基础数值保持现有资源配置：

- 符文刻匠：突击，装备物品的友军获得强化+3，保留至下一次实际行动消耗或本场结束，移除旧倍率光环。
- 盾墙列兵：增加耀眼；既有乡邻获得护甲额外+1保留，额外护甲不递归触发自身。
- 伙夫：增加耀眼；突击时双方每个生效火符文给此卡本场生命+2，移除旧5枚上限，最大生命与当前生命同时增加。
- 随军医者：治疗遮蔽一处生效伤势至战斗结束。沿用既有最高伤势等级优先、同级随机选择；已遮蔽者不进入候选，战后恢复原伤势，不永久治愈。
- 悲歌诗人：每个其他非衍生友军被消灭，诗人自身左右两侧存活友军各获得本场热诚+1。用户已确认邻居以诗人自身为参照；移除旧自身行动值、护甲增长和3次上限。

## 2. 关键数据、节点与函数

| 文件／数据 | 职责 |
| --- | --- |
| `scripts/ui/card_service_slot.gd` | 共用强化／服务空槽。`show_card()`由`resolve_card_view`取得现有卡面，记录`_source`的父节点、位置、尺寸与拖放状态，再临时搬入；`return_card()`恢复原节点状态，`card_returned`通知协调者清空选择。 |
| `scripts/main.gd` | 设置商店层级；为共用槽寻找战场或收藏中的真实卡面；处理`card_service`拖放；交易、读档、还原前归还节点。`_resolve_pending_random_cards()`复用现有卡池资格与随机源。 |
| `scripts/flow/short_maze_controller.gd` | 保存强化目标实例ID，创建强化空槽和选项；刷新、退出和事务回退时归还原卡面；商店事件仍显示哨位库存。 |
| `scripts/ui/card_view.gd` | `show_new_card_marker`限定绿点的显示语境。只有收藏节点开启它；`OwnedCard.is_new`继续保存标记状态。服务中暂时关闭，归还时恢复。 |
| `scripts/ui/squad_view.gd` | 原小队保留实例绑定，刷新时跳过被服务槽暂存的CardView，避免把它移回原位或改掉拖放来源。 |
| `scripts/ui/celestial_indicator_controller.gd` | 指示物板和库存挂在Main设计画布下，保持固定坐标；自由放置、绑定、取消回位规则沿用。 |
| `scripts/data/battle_settlement_service.gd` | 在结算提交前调用随机卡解析回调。解析失败恢复收藏、奖励与资源状态；Main同时恢复随机源。 |
| `data/demo2/ash_ledger_effect_samples.json`和五张`.tres` | JSON保存正式效果条件、目标、操作和持续期；`.tres`保存卡面短文案、关键词与原基础数值。运行时只新增必要的装备条件，复用已有强化／护甲／生命／遮蔽／热诚操作。 |

## 3. 初学者需要理解的Godot／GDScript写法

**Node与Resource分工。** CardView是显示与输入节点；OwnedCard是本局卡牌数据；CardData是共享定义。移走CardView不会移除OwnedCard，也不应该复制一份OwnedCard。只有确认出售／撕卡才删除实际拥有实例。

**`reparent(parent, false)`。** 这是把同一个节点换到另一个父节点。这里不保留旧全局坐标，因为卡槽会立即给它新局部位置；先保存旧父节点、位置、缩放与拖放状态，归还时再恢复。它与`instantiate()`创建新节点不同，保证槽里的卡就是玩家拖入的原卡面。

**Callable与signal。** 空槽用Callable询问合法性、寻找卡面，完成归还后发signal。这样同一节点能用于强化和商店，而费用、规则、存档仍分别由协调者处理。结算服务也用Callable交给Main按当前正式卡池解析奖励，不另造一套卡池。

**`set_meta()`临时标签。** 原小队仍记录这个CardView，但节点已在槽内。`card_service_slot`标签让原小队刷新跳过它，避免两个容器同时控制一个节点的位置；归还时删除标签。这个标签仅属于运行时UI，不进入存档。

**事务与稳定实例ID。** 随机卡请求先在复制的随机源上选完，再创建OwnedCard；成功才推进正式随机源并清空请求。结算日志按battle_instance_id去重，能防重复发奖。新同名卡在战场中可能使用独立CardData引用，因此测试应核对它绑定的OwnedCard和实例ID，不能要求它与另一张同名卡的CardData是同一对象。
