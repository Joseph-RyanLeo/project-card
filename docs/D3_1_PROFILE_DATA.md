# D3-1 每档局外数据实现与验证

日期：2026-11-02。已在主目录、main分支串行实现；未提交或推送Git。启动授权与范围见D3-0第1节。本阶段完成数据及必要存取接入，后续阶段不自动开工，学习问答／练习继续暂停。

后续状态：D3-2已接通整局计分、总结、本次收藏完整界面和单卡战绩提交；本文保留D3-1阶段记录，最新功能与验证见[D3-2说明](D3_2_RUN_END_IMPLEMENTATION.md)。

## 1. 整体流程

每档仍使用原来的一个JSON文件：第一档`project_card_run.json`，第二／第三档`project_card_run_2.json`、`project_card_run_3.json`。原本局字段不改名，新增独立版本的`profile_progress`段。局内与局外在同一个文件事务提交，不出现本局保存成功、另一份局外文件保存失败的情况。

`profile_progress.profile`保存跨局进度；`profile_progress.run`保存本局身份、待提交发现、任务进度与待完成收藏。新局只重建`run`和原有局内状态，保留`profile`。普通保存、退出、崩溃恢复和单场战后均不调用整局积分奖励。

当前运行继续使用Demo2的八天迷宫、英雄和供给逻辑；局外解锁数据基线为0积分、伊奥恩与灰烬证册、免费教程资格。D3-1没有将完整教程、任务试用或所有卡池限制提前接入；不能把数据基线误认为全部D3玩法已开放生效。

## 2. 数据职责

- `scripts/data/profile_progress.gd`：每档数据、阶段校验和数据操作。`profile.points`是积分余额；`discoveries`按卡牌／贴纸／资源身份去重；`tasks`保存购买与完成；`unlocks`分英雄、卡包、道具、路线与成长；`collection`是卡牌稳定ID到固定顺序单卡数组的映射；`receipts`避免同一奖励凭证再次入账；`pack_choices_by_hero`保存按英雄的3个可选包记忆。
- `profile.created_at`记录建档时间，旧档未知为0；`legacy`区分Demo2迁移。教程状态区分实际完成、跳过与引导奖励已发，并在新档创建时冻结`skip_eligible_at_creation`。查询其他现存档的实际教程完成仅用于此资格，不复制其他档积分或进度；不按槽号判定首档。教程流程尚待后续接入，此阶段仅提供数据与一次性引导奖励操作。
- `run.id`使用独立随机身份，每局更新；`run.stage`为`active`（本局）、`selection`（选卡）、`preview`（集合预览）、`hub`（局外）。`run.tasks`分`main`／`side`保存当局目标进度；新局重置目标进度，购买资格留在局外。`read_tutorial_hints`保存本局已阅教学标识。
- `scripts/data/owned_card.gd`：原实例状态增加`acquired_at`、`acquisition_source`、`recruited_by`、`lifetime_stats`。英雄稳定ID复用配置的`ioann_warden`。获得时间不会在入藏时重写；来源尽量保留包、事件、战斗或来源卡信息，未知不造历史。
- `scripts/data/owned_card_collection.gd`：本局单卡唯一容器；新增随快照保存的`acquired_discoveries`获得账本，解决先获得再卖出的卡发现丢失，同时保证失败交易恢复收藏快照时撤销未成功获得的发现。移除信号在正常耗尽法术移除前保存其完整快照。
- `scripts/data/run_save_service.gd`：继续复用现有卡牌JSON编码／解码，原本局格式版本仍为9；局外段独立版本为1，历史元数据字段在旧档中可缺省。加载局外数据先校验，失败不覆盖当前数据或写默认值。
- `scripts/main.gd`：`profile_progress`是当前档的局外数据对象；`save_run_to_path`把它与本局一次写入；`save_profile_action`负责数据动作失败／落盘失败时恢复原局外状态；`begin_run_collection`冻结候选，供后续整局结算调用。
- `scripts/flow/short_maze_controller.gd`：原事件事务扩展到局外数据，事件结束／离店提交发现，失败整体回滚；开局初始物资发现统一提交；不允许待完成收藏时重开。
- `scripts/data/run_slot_service.gd`、`scripts/ui/game_display.gd`、`scripts/ui/start_menu.gd`：三档摘要与删除、备份识别、按保存阶段恢复。四层菜单已在本阶段收尾接入：空档先保存纯局外数据并进入大厅，手动开局才创建Main；待完成收藏直接恢复摘要和确认。完整菜单／设置／路由及截图见[菜单说明](START_MENU_IMPLEMENTATION.md)。完整选卡、并排检视与展览馆仍由后续阶段实施。

## 3. 发现与回滚

1. 获得单卡写入本局获得账本；即使随后卖出，也能保留该事件真实获得的信息。普通衍生卡由生成源预览，衍生资源仍记录资源图鉴。
2. 中间保存扫描自有卡的纹章／伤势／元素贴纸和已入工具箱贴纸，写入`run.pending_discoveries`；未入包的临时掉落不作为实际入包发现。此时不独立提交永久图鉴。
3. 事件完成／离店，与本局结果一起正式提交。实际成功开采资源的身份附在既有战斗奖励账本中，正式战后提交；不凭普通观看或敌方持有记录发现。
4. 开战前另存局外本局快照。战斗中保存使用战前本局与战前局外待提交状态；读档／重试不会留下本场未提交发现或目标进度。正常战后仍沿用已有结算凭证。
5. 保存失败不接受本次局外数据动作，事件事务仍恢复原本局／局外快照。购买资格和完成奖励API只负责已确认结果的数据操作；正式价格、前置、目标判断由后续任务服务提供，不存在新编的任务树。

## 4. 收藏提交

后续整局结算调用`begin_run_collection`后，冻结当前持有的非衍生、非资源卡及本局正常耗尽法术。候选仍使用完整实例编码；`archive_id = run.id + 本局instance_id`，避免下一局重复的`run_card_000001`与旧收藏撞身份。

`set_selection`最多接受8张具体候选；每项指定`candidate_id`与`slot`。同种从左向右填空位，最多3位；满位替换需同时提供原`replaced_id`与`replacement_confirmed=true`，并拒绝重复单卡、重复目标位置、空洞和失效替换。预览只保存选择，不修改旧收藏。最终`confirm_collection`一次提交全部入藏／替换，保持原位置；法术此时才恢复全新使用次数，其他实例状态保持。

保存选卡或预览阶段时，候选、选择、替换关系及阶段全部保留。读档优先进入对应阶段，禁止原局内操作和新开局；0张也必须预览后最终确认。恢复／确认收藏不发积分。被替换的单卡从当前正式收藏移出，不提供收藏历史或回收站；磁盘备份是异常保存保护，不是玩家可访问的收藏历史功能。

## 5. 保存、删除与旧档

先完整写入同目录`.tmp`并检查写入错误；存在主档时先复制为`.bak`，然后原子重命名临时文件覆盖主档。复制或替换失败不会先移走有效主档。保留上一版备份；若旧写入流程中断导致主档缺失而备份仍在，可从备份读取。主档存在但损坏时拒绝加载，不静默用旧备份覆盖当前文件。

删除档位只处理该档JSON、`.tmp`、`.bak`和对应`.diagnostics.jsonl`，包含所有局内／局外数据；其他档不变。`run_slots.cfg`仅为所选档位偏好，不含共享进度。

Demo2缺少局外段时，保留原收藏／阵容／金币／迷宫／随机流等可恢复内容，补充局外基线，完成既有校验后才写回。稳定旧局身份由文件路径派生；不按旧金币兑换积分，不由八天通关推测教程完成，不重建历史获得／战绩／收藏。当前仍持有的实际内容可继续产生发现；已卖出或已耗尽且旧档没有记录的内容无法恢复。原卡牌迁移规则仍由原存档服务处理。

## 7. 初学者需要理解的写法与未覆盖范围

`RefCounted`适合保存纯数据，不需要挂到场景树；`OwnedCard`仍是每张具体卡的Resource，卡牌共享定义继续留在`CardData`。`duplicate(true)`复制嵌套字典／数组，防止改预览或失败动作时连带改动正式收藏；卡牌实例仍通过已有编码器转换成可写JSON的数据。`Callable`把“本次要执行的数据动作”交给统一保存入口，因此每个按钮不必另写一份回滚。验证对象先临时构造、全部合法后才替换正式状态，避免读到一半污染当前游戏。

累计战绩字段支持保存与恢复，但本阶段**没有接入全部战斗事件的单卡归因／累计**；新档未采集项留空，不能据此宣称伤害／复活阵亡等统计已经实现。四层菜单及存档路由已完成收尾；完整局后计分公式与总结、确认放弃时的正式战斗提交、整局结束自动转收藏、完整选卡／并排检视／图鉴、任务树与商品、D3卡池限制、正式教程连续流程和局外调试面板均由对应后续阶段实施。没有导入镀金建议效果、补造莉丝忒卡牌、任务树或未定目标／配方。
