# 拖动与战斗性能检查（2026-10-24）

## 结论

本机已复现局部短顿，不能笼统称为“完全不卡”。持续拖动没有复现持续性掉帧或卡死；主要慢帧在装备成功松手、打开商店、开战、战斗结算，以及密集弹道同时频繁换位的压力场景。

本次只做诊断，没有修改正式游戏逻辑、美术、动画时长、玩法参数或存档格式。已有未提交改动保留。

## 测量方法与边界

- Apple M4、16 GB、macOS、Godot 4.7.2 Steam、Compatibility/OpenGL。
- 交互使用真实2560×1440窗口，内部1280×720画布，垂直同步开启，未设置最大帧率；实际空闲帧间隔约8.3毫秒，不能按固定60Hz解释所有帧。
- 使用正式场景、真实卡牌实例、真实鼠标按下／移动／松手和正式拖放提交。基础收藏补至72张，再加入操作与阵容用实例；不是只有一张卡的空场景。
- 连续拖动每类100帧、服务槽互拖300帧；另测装备、资源、法术各3次成功松手，以及资源板内移动、法术队列重排。两组交互共6001个帧样本、43项行为检查全部通过。
- 帧耗时使用 `Time.get_ticks_usec()` 的实际帧间隔，不用可能被引擎平滑的 `delta` 替代。另记录输入分发同步CPU耗时和Main已有的分段计时。
- P95表示95%的样本不超过该值。60FPS预算约16.67毫秒；33.33毫秒约为两个60Hz帧预算，超过50毫秒视为更明显的单次停顿。没有把“低于33毫秒”说成稳定60FPS。
- 单次开始／结束操作不计算有统计意义的P95。父函数计时包含子函数，不能相加；输入CPU时间与整帧时间也不能相加。
- 自动化寻找目标时，`_show_owned()` 会扫描并重建收藏页；重建测试场景和生成事件也有50～115毫秒的夹具尖峰。这些明确标为setup，未算作玩家持续拖动卡顿。
- 没有独立采集GPU时间，也没有Windows实机或特定玩家存档；不能把未归因时间全部归为GPU，更不能外推其他设备帧率。

## 密集弹道与频繁换位压力

复用已有 `tests/performance/battle_load_probe.gd`，实际渲染1280×720、关闭垂直同步。28张随从、每张冷却0.5秒、全部三暗符文、提高生命以维持负载；每种负载预热10帧，再手动按1/60秒推进240帧。它是高强度压力场景，不等同于普通战斗；换位场景另外每6帧触发4次正式换位，共160次。

| 场景 | 帧耗时：中位／P95／最大 |
| --- | --- |
| 密集弹道，507次弹道，效果节点峰值310 | 8.76／18.84／73.92毫秒 |
| 弹道＋频繁换位，589次弹道，额外160次换位 | 15.56／38.89／62.84毫秒 |

同步规则推进P95分别约13.04／13.39毫秒。两组规则批处理 `_resolve_ready_batch()` 单次最大约44.79／43.63毫秒；卡面状态同步单次最大约3.90／4.11毫秒，弹道创建单次最大约4.47／0.47毫秒。计时互相包含，不相加。规则批处理是已测到的CPU尖峰入口，不能简单归为“弹道图片太多”。

## 后续优先级

1. 装备成功松手：精确吸附只有约1.6毫秒，已定位到约10毫秒收藏重建与约4毫秒准备预览刷新，优先合并或复用这些显示更新，不应先削减吸附精度。
2. 开战与结算：检查同一事务中的卡面恢复、状态刷新、收藏重建及存档分段；本轮确认了总耗时，尚未对每个子步骤完整拆分计时。
3. 高频战斗规则批处理和换位：围绕已定位的批处理入口继续分段，不减少规则事件、弹道或动画来掩盖卡顿。
4. 持续拖动保持现有行为；本轮没有发现足以优先重构拖动系统的持续性性能问题。

## 如何读懂本次诊断

输入流程仍是鼠标事件→原有拖放目标判断→松手提交→卡面／阵容刷新，或者战斗控制器推进规则→发出状态／特效事件→Main更新显示。诊断只在这些真实入口外计时，不替换业务函数。

`main.gd` 的 `_record_battle_performance_frame()` 记录规则、拖放和界面计时；装备还可通过 `PROJECT_CARD_TRACE_EQUIP_DROP=1` 开启已有分段日志。临时脚本额外记录跨帧真实时钟间隔与输入分发时间。压力探针的子类用 `super.函数()` 调用正式逻辑，只增加计时。

`await process_frame` 会等到下一次帧信号，所以等待前后的时间包含渲染与其他节点工作；它不是某一个函数的纯CPU耗时。P95能描述多数帧，但会隐藏少数尖峰，因此必须同时看最大值、超过预算的帧数，以及尖峰发生时的业务阶段。
